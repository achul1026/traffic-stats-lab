# 설계 결정 기록: 무엇을 선택했고, 무엇을 포기했나

이 문서는 측정 결과(`results/results.md`)에서 읽을 수 있는 내용과, 읽을 수 없는 내용을 구분해서 적는다.

## 1. 월 단위 파티셔닝

- **선택**: `obs_time` 기준 월 단위 RANGE 파티션 24개.
- **측정으로 확인된 것**: 기간 조건이 있는 조회는 해당 월 파티션만 읽는다.
  Q1(3개 월)은 파티션 3개, Q2(1개 월)는 파티션 1개만 읽었다. 인덱스 없이도 Q1이 1,783ms → 290ms(6.1배).
- **측정으로 확인된 것(역효과)**: 기간 조건이 길어 파티션 12개를 읽는 Q4는 단일 테이블보다 느렸다
  (2,947ms → 6,774ms, 중앙값. 최소값도 4,485ms로 단일 테이블보다 느림).
  **이유는 확인하지 못했다.** 병렬 실행 계획 차이일 가능성이 있지만 이 저장소의 측정만으로는 단정할 수 없다.
- **포기한 것**: 파티션 수가 늘면 계획 수립 비용과 관리 부담(파티션 생성·삭제 자동화)이 생긴다.
  이 실험은 24개라서 문제가 되지 않지만 일 단위 파티션(730개)은 시험하지 않았다.
- **고르지 않은 대안**: 일 단위 파티션(관리 부담 증가), 지역 기준 파티션(조회 조건이 대부분 기간이라 효과 작음).
  *두 대안은 이 저장소에서 직접 측정하지 않았다.*

## 2. 인덱스: `(region_id, obs_time)`, `(road_id, obs_time)`

- **측정으로 확인된 것**: 조회 조건과 맞는 Q3(도로 + 기간)은 1,757ms → 62ms(28배)로 크게 빨라졌다.
- **측정으로 확인된 것(역효과)**: 넓은 기간을 읽는 Q2는 단일 테이블에서 인덱스 사용 시 2,525ms → 5,559ms로 **느려졌다**.
  계획기가 인덱스(비트맵 스캔)를 골랐지만 전체의 상당 부분을 읽어야 해서 순차 스캔보다 불리했다.
  Q4는 인덱스가 있어도 순차 스캔을 택했다. 인덱스는 "항상 이득"이 아니라 읽는 비율이 작을 때만 이득이다.
- **함께 쓸 때**: 파티션 + 인덱스(D)가 Q1에서는 파티션만(B)보다 느렸다(500ms vs 290ms). 파티션이 이미 범위를 좁혔기 때문에 추가 인덱스가 이득이 되지 않았다.
- **포기한 것**: 인덱스 2개가 데이터와 비슷한 크기(각 902MB)다. 쓰기 비용과 저장 공간이 늘어난다.
  *쓰기 성능은 이 저장소에서 측정하지 않았다.*

## 3. 일 단위 집계 테이블(`daily_region_stats`)

- **선택**: (지역, 일) 단위로 `통행량 합계`, `속도 합계`, `건수`를 미리 계산해 저장한다. 평균은 (속도 합계 / 건수)로 구해서 합산 후에도 정확하다.
- **측정으로 확인된 것**: Q1 5.8ms, Q2 11.2ms, Q4 11.9ms로 원본 대비 225~307배. 결과가 원본 조회와 일치함을 `results/verification.md`에서 확인했다.
- **포기한 것**: ① **데이터 지연** — 이 실험에서는 배치로 한 번에 만들었다. 실시간 반영은 구현하지 않았다.
  ② **질의 유연성** — 집계 단위(지역·일)에 없는 조건(도로 단위 Q3)은 답할 수 없다.
  ③ **정합성 관리** — 원본이 정정되면 집계도 다시 만들어야 한다. *이 부분은 구현하지 않았다.*
- 평균을 `평균의 평균`이 아니라 `합계/건수`로 저장한 이유: 평균은 합산하면 값이 틀어지기 때문이다.

## 4. 측정 방법에서의 선택

- `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`의 실행 시간을 사용했다(서버 안 실행 시간, 클라이언트 전송 시간 제외).
- 워밍업 1회 후 5회 측정의 **중앙값**을 사용했다. 최소·최대는 `results/timings.csv`에 있다.
- 모든 변형이 같은 답을 내는지 먼저 확인했다(`bench/verify.py`).

## 5. API 계층의 캐시(Redis)

- **선택**: 집계 조회 결과를 Redis 에 5분(TTL) 저장. 키는 (질의, 대상, 파라미터) 전체.
- **TTL 근거**: 통계 화면은 몇 분 늦어도 되고 집계 테이블 자체가 일 단위라는 *가정*이다. 실제 요구사항으로 검증한 값이 아니다.
- **측정으로 확인된 것**: 집계 테이블만으로도 이미 빨라서(수 ms~수십 ms) 캐시의 추가 이득은 질의마다 달랐다.
  Q4(지역 순위)는 585 → 1,413 req/s로 늘었지만, Q1(월별 통행량)은 1,605 → 1,414 req/s로 **차이가 없거나 오히려 낮았다**(측정 오차 범위).
  이미 충분히 빠른 질의에는 캐시가 이득이 아니고 복잡성만 더할 수 있다.
- **포기한 것**: 캐시 무효화(원본·집계가 갱신될 때 캐시를 지우는 일)는 구현하지 않았다. 지금은 TTL 만료에만 의존한다.

## 6. 캐시 장애 대응: 폴백 + 서킷 브레이커

- **처음 구현**: 캐시 읽기·쓰기 오류가 나면 로그만 남기고 DB 로 조회(응답 실패 0건).
- **측정으로 드러난 문제**: Redis 를 껐더니 요청은 모두 성공했지만 **요청당 약 1초**(처리량 17.9 req/s)로 느려졌다.
  요청마다 캐시 읽기 타임아웃과 쓰기 타임아웃을 연달아 기다리기 때문이다.
- **수정**: 캐시 오류가 나면 10초 동안 캐시를 건너뛰는 서킷 브레이커(`CacheBreaker`)와 타임아웃 단축(500ms → 200ms).
- **수정 후 측정**: 같은 상황에서 p50 1,018ms → 20ms, 처리량 17.9 → 674 req/s. Redis 를 다시 켜면 약 10초 안에 자동으로 캐시를 다시 쓴다.
  (`results/load/redis_down_Q2_before.txt`, `..._after.txt`)
- **포기한 것**: 실패 횟수 기반의 정교한 브레이커(half-open 상태 등)가 아니라 단순 시간 기반이다. 라이브러리(Resilience4j 등)는 쓰지 않았다.

## 7. 부하 테스트 도구: ApacheBench(`ab`)

- k6 대신 macOS 에 기본 설치된 `ab` 를 사용했다(추가 설치 없이 재현 가능).
- **한계**: 부하 생성기와 서버(API, DB, Redis)가 같은 노트북에서 돌아 서로 자원을 나눈다. 절대값보다 변형 간 상대 비교로 읽어야 한다.
  `ab` 는 시나리오(여러 단계 요청)나 점진적 부하 증가를 지원하지 않는다.
